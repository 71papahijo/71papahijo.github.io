FPGA Snake Game

This project recreates Snake entirely in FPGA hardware, using a finite state machine to control game flow, VGA output to draw the board, and switch-based input for movement. The final build renders a playable snake, spawns apples through state-driven logic, and demonstrates how game behavior can be modeled directly in hardware.

A major part of the project was balancing gameplay features against the logic capacity of the FPGA. That meant making deliberate tradeoffs in grid size, apple generation, and maximum snake length so the design would fit and remain stable.

Project Overview

The game was inspired by a classic Snake implementation and built as a modular hardware project with separate logic for movement, visuals, apple generation, and top-level integration.

Gameplay Goal

A green snake moves across the screen, grows as it eats apples, and ends the run when a finish condition is reached. The project evolved from simple collision rules into a more polished version with screen wrapping and additional control states.

Hardware Structure

The design was organized around a top module that connected movement controls, game logic, apple generation, and VGA display timing. That modular setup made it easier to debug each subsystem independently.

Key Tradeoffs

Because hardware resources were limited, the design traded off random apple generation, board size, and maximum snake length in exchange for a working implementation that could actually fit on the FPGA.

FSM State Design

The finite state machine controls when the game is waiting, actively running, or showing a finished condition. Two especially important states are idle and end, because they define the transitions into and out of gameplay.

Idle State

The idle state acts as the game's reset and waiting screen. In this state, the snake is not advancing through the playfield, and the design can hold the initial position, clear stale movement data, and wait for the player to begin.

  • Establishes a clean starting condition for the snake and apple logic.
  • Prevents unintended movement before player input is valid.
  • Provides a stable handoff into the running state once play begins.

End State

The end state is reached when the game has finished, either because the snake hits a terminating condition or the win target has been reached. Instead of continuing to update movement normally, the FSM locks the game into a final display condition so the result is visible to the player.

  • Stops normal gameplay updates after a terminal event.
  • Lets the design show a clear visual indication that the run is over.
  • Creates a reliable point for restarting or returning to idle.

FPGA Size and LUT Usage

One of the biggest engineering challenges in this project was simply fitting the game into the FPGA. An early version of the game logic alone exceeded the device capacity, using more than 110% of the available logic resources. The synthesis output also showed a failed placement attempt against a device with 1,399 ICESTORM logic cells.

In practical terms, this meant the design had to be reduced and reorganized. The snake body was stored as an N × M register representation, where each cell tracked whether part of the body occupied that location. That approach works well conceptually, but it becomes expensive in LUTs when the board grows larger and when the full body history has to be shifted every update.

  • The board indexing was downsized to reduce resource usage.
  • The maximum snake length was capped so the body array stayed manageable.
  • Apple generation moved to a deterministic FSM-based approach instead of a more expensive random system.
  • The final implementation prioritized fitting, timing clarity, and stable behavior over extra features.
Fitting the design was not just a performance issue. It shaped the entire architecture of the game. Features like random apples, a larger board, and a longer snake all had a direct hardware cost, so the final build reflects a set of deliberate logic-budget decisions.

Implementation Challenges

Two bugs had a large impact on the final design. First, apples could appear on top of the snake body, which made gameplay inconsistent. Second, body shifting originally happened before the tail update, which left incorrect body fragments behind on the screen.

Fixing those issues required enforcing the correct update sequence in hardware. That improved correctness, but it also increased the design effort and reinforced the importance of clean state transitions between movement, growth, and rendering.

Final Result

The finished project demonstrates a playable Snake game on FPGA with VGA output, switch controls, apple spawning logic, and explicit state transitions. Even with resource constraints, it shows how a familiar game can be rethought as a digital design problem involving control flow, storage, synchronization, and optimization.
